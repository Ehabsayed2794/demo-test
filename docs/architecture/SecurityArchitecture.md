## Bidding write authority (Sprint 3.8)

Answering this document's own required questions directly, per the brief:

- **Who owns bids?** Each seat owns its own bid, and only its own. Ownership is defined by `matches/{matchId}.seats[seatId]` — the map `isValidNewMatch()` establishes once, at creation (see `SeatIdentityModel.md`), and which `isValidBidSubmission()` never permits to change afterward (`seats` is not in that rule's allowed-changed-keys list at all). There is no "match owner" or "dealer" write authority over another seat's bid — the dealer's own bid is owned by the dealer's own seat, exactly like every other seat.
- **Who may write?** Exactly one person per seat: the uid `seats[seatId]` names, and only for that seat, and only while `biddingOpen == true`, and only if that seat hasn't already bid. `MatchService.submitBid(matchId, seatId, bid)` is the one code path that produces this write — it derives the caller's own uid from `SessionService` internally (never a parameter), so there is no argument for a caller to misuse to write as someone else; `firestore.rules`' `isValidBidSubmission()` independently re-derives and re-checks the identical ownership fact server-side, from `request.auth.uid`, trusting neither the client's JS nor its own request body's `lastBidSeat` claim alone.
- **Who may read?** Unchanged since Sprint 3.4: only a player listed in the match's own `players[]` (`allow get`). Bids are visible to every seated player the moment they're written (a `bid` amount isn't a secret in this game the way a hand of cards is — see `FirestoreSchema.md`'s "hands problem," which bidding does not reopen or worsen).
- **How does version work?** `version` starts at `1` when the match is created and must increase by **exactly** `1` on every accepted write (`newData.version == oldData.version + 1`) — checked independently by the rule, not merely produced correctly by client code that could be buggy or malicious. This is the Task 2 "ordering guard, made real": combined with Firestore's own transaction-level optimistic concurrency (every write happens inside `db().runTransaction()`), a stale, duplicated, or out-of-order write is rejected both at the app layer (the transaction re-reads fresh data on conflict) and, independently, at the rules layer (a version that isn't exactly current+1 is denied outright, regardless of how it was produced).
- **How does concurrency work?** Two clients racing to write the SAME document (whether the same seat or different seats) are serialized by Firestore's transaction mechanism itself — whichever commits first wins that version number; the other's transaction callback is automatically re-run against the now-current document. `submitBid()`'s own checks (already-bid, seat ownership, bidding-open) are re-evaluated on every such retry, so a losing racer for the SAME seat correctly fails with `ALREADY_BID` rather than silently overwriting the winner, while two racers for DIFFERENT seats both succeed, serialized into two sequential version increments. See `docs/architecture/MatchSynchronization.md`'s Sprint 3.8 section and `tests/submit-bid.test.cjs`'s "two simultaneous bidders" tests (MOCKED) for the concrete, executable proof of both cases.

## Compile-safe Rules syntax (Sprint 4.2.3 — Firestore Rules Compile-Safe Card Turn Hotfix)

**A direct review of the shipped `firestore.rules` found a real, previously-unnoticed risk in HOW this project had been verifying its own rules, not in what those rules were trying to express.** Every prior sprint's `tests/rules-simulation.test.js` re-implements each rule's INTENDED logic in plain JavaScript and exercises that JS against representative inputs — an honest, explicitly-labeled SIMULATED substitute for the Firebase Rules Unit Testing library, which needs the Firebase CLI and a Java-backed local emulator (neither available in this sandboxed project). **That JS simulation can prove logical intent. It cannot prove `firestore.rules` itself compiles**, because it does not parse or execute real CEL (the language Firestore Rules is actually written in) — it only proves "this JS re-implementation of what the rule is SUPPOSED to do behaves as intended." This gap let an unsupported construct ship, undetected, for two full sprints (4.2 and 4.2.1/4.2.2): `oldData.seats.keys().exists(s, oldData.seats[s] == newData.turn)`, using `.exists()` — a List method that is not part of Firestore Rules' officially documented List method surface (https://firebase.google.com/docs/reference/rules/rules.List). The corresponding JS simulation used `Array.prototype.some()`/`.indexOf()`, which of course compiles and runs fine as JavaScript — proving nothing about whether the CEL it was meant to mirror does.

**Fixed in Sprint 4.2.3** by auditing the entire file for `.exists(`, `.all(`, `.any(`, nested `.diff(`, lambda-style syntax, and undocumented collection/list iteration, and replacing every occurrence found with explicit, compile-safe, officially-documented syntax:
- `isValidCardSubmission()`'s turn check (the originally-flagged line) — rewritten to explicit `Map.get('p1'/'p2'/'p3'/'p4', null)` lookups against the 4 fixed, canonical seat keys, OR'd together, instead of iterating `.keys().exists(...)`.
- `isValidSeatMap()`'s bijection checks (`seatKeys.all(s, seats[s] in players)` and a nested `seatKeys.all(s1, seatKeys.all(s2, ...))` self-join) — rewritten to the same explicit `Map.get(key, null)` pattern: 4 individual "does this seat's uid belong to `players`" checks, plus the 6 explicit pairwise inequality checks a 4-element self-join reduces to.
- `isValidNewMatch()`'s "every bid starts null" check (`data.seats.keys().all(s, data.bids[s] == null)`) — same explicit 4-seat rewrite.
- `isValidBidSubmission()`'s `biddingOpen` computation (`oldData.seats.keys().all(s, s in newData.bids && newData.bids[s] != null)`) — same explicit 4-seat rewrite, using precomputed per-seat `let` bindings.

Every occurrence of `.diff(...).affectedKeys().hasOnly([...])` elsewhere in the file (the `players/{uid}` and `rooms/{roomId}` field-restriction rules, and the un-flagged parts of `isValidBidSubmission()`/`isValidCardSubmission()`) was individually re-checked and found to be genuinely, officially documented (`Map.diff()`, `MapDiff.affectedKeys()`, `List.hasOnly()` are all real, catalogued methods) — none of those needed to change. `.exists(/path/).data` (the room/match existence checks used elsewhere, e.g. `isValidNewMatch()`'s `exists(/databases/.../rooms/$(data.roomId))`) is a DIFFERENT, unrelated, officially-documented top-level Rules function (path existence), not the List method this sprint's finding is about — not touched, not miscategorized.

**None of these rewrites change gameplay behavior, schema, `MatchService`, `MatchAdapter`, or `TableEngine` — they change ONLY the CEL expression used to enforce an identical, pre-existing rule.** Every replacement is semantically identical to what it replaced: since `seatKeys.hasOnly(['p1','p2','p3','p4'])` already restricts `seats`' keys to the fixed 4-slot set, enumerating `p1`..`p4` explicitly (treating an absent seat, `.get(key, null) == null`, as contributing no constraint) reaches the exact same verdict as iterating over whichever of those 4 keys happened to actually be present.

**Honest, restated limitation**: replacing `.exists()`/`.all()` with explicit, officially-documented syntax closes the specific risk this review found — but this project's own JS rules simulation STILL cannot prove `firestore.rules` compiles. It never has, and this sprint does not change that. Real verification that the rules file compiles and behaves as intended against the actual Firebase Rules engine requires either the Firebase Rules Playground/compiler or the Firebase Emulator Suite — **neither has been run against this project's `firestore.rules`, this sprint or any prior one.** `tests/rules-simulation.test.js`'s SIMULATED label has always meant, and continues to mean, "logical intent verified in a JS re-implementation" — never "proven to compile," and this document does not claim otherwise.

## Card write authority (Sprint 4.2, hardened Sprint 4.2.1, extended Sprint 4.2.2)

- **Who owns a card play?** Each seat owns its own submissions to `cardLog`, exactly like bids — ownership is the SAME `matches/{matchId}.seats[seatId]` map, still never re-assignable through any write path.
- **Who may write?** `MatchService.submitCard(matchId, card)` is the one code path — it takes NO `seatId` parameter at all (stricter than `submitBid()`'s "claim a seat, then verify" shape); the acting seat is resolved purely from the calling uid via `MatchAdapter.uidToSeat()`, so there is no argument for a caller to even ATTEMPT submitting as a seat they don't own. **Sprint 4.2.1 closed a Critical gap here**: the ORIGINAL Sprint 4.2 version of this function never checked WHOSE TURN it currently was at all — any seat-owner could write regardless of turn order. It now calls `MatchAdapter.assertLocalTurn()` — the SAME authority gate Sprint 4.1 built for exactly this purpose — BEFORE ever opening a Firestore transaction, rejecting `NOT_YOUR_TURN` with zero writes attempted if it isn't. See `docs/architecture/EngineAdapter.md`'s Sprint 4.2.1 section for the honest caveat this inherits: the gate's accuracy still depends on `matches/{matchId}.turn` actually being current during the PLAY phase, which nothing in this codebase writes back yet — the SAME pre-existing gap Sprint 4.1 already documented for bidding, not newly introduced or newly claimed to be fixed here.
- **Is the card itself checked for legality before it's written?** **Sprint 4.2.1 closed the SECOND Critical gap**: the original version validated only a GENERIC shape (a real suit, a real rank) and wrote first, leaving legality entirely to whichever client later replayed the log — meaning an engine-rejected card stayed in `cardLog` PERMANENTLY once written, since nothing purged it. `submitCard()` now asks the real `TableEngine.canPlayCard()` (a pure, non-mutating query against the SAME `isLegal()`/`state.turn`/`state.phase` checks `emit()` already performs) whether the play would be accepted, BEFORE the transaction opens — an illegal card is rejected `ILLEGAL_CARD` with zero writes attempted. `firestore.rules`' own `isValidCardSubmission()` still does NOT (and structurally cannot, without re-implementing `table-engine.js`'s follow-suit logic in CEL — exactly the "duplicate gameplay rules in Firestore" this whole project forbids) check legality server-side; the CLIENT-side pre-write gate is what actually closes this specific defect, not a rules change.
- **How does version work?** Identical mechanism to bidding — `version` must increase by exactly 1, checked independently by `isValidCardSubmission()`, layered on Firestore's own transaction-level optimistic concurrency.
- **Does the write also advance whose turn it is next? (Sprint 4.2.2)** Yes, atomically, in the SAME write as the card append — closing a Critical gap Sprint 4.2.1 left open: `submitCard()` previously appended the card but never updated `matches/{matchId}.turn`, so the NEXT seat's own submission was incorrectly rejected as `NOT_YOUR_TURN` (Sprint 4.2.1's own tests hid this with a test-only manual turn mutation between submissions — never a production write). `submitCard()` now calls a new, purely additive, non-mutating `TableEngine.previewPlay()` query BEFORE the transaction to learn the intended next seat/phase, and writes `cardLog`, `lastCardSeat`, `turn`, `cardPhase`, and `version+1` all in one `tx.update()` call. `isValidCardSubmission()` was extended IN PLACE (an UPDATE rule evolves in place in this project, unlike CREATE rules, which get versioned suffixes) to independently verify: the caller owned the PREVIOUS active turn (`oldData.turn == request.auth.uid`); the NEW turn is either `null` or a UID present among `oldData.seats`' own values; and `newData.cardPhase in ['PLAY', 'RESOLVING']`. **Sprint 4.2.3 (Firestore Rules Compile-Safe Card Turn Hotfix) correction**: the "UID present among `seats`' own values" check was ORIGINALLY expressed as `oldData.seats.keys().exists(s, oldData.seats[s] == newData.turn)` — a direct review found `.exists()` is not part of Firestore Rules' officially documented List method surface, so this project's own JS rules simulation could never have proven it actually compiles. Rewritten to explicit `Map.get('p1'/'p2'/'p3'/'p4', null)` lookups against the 4 fixed seat keys, OR'd together — see this document's own "Compile-safe Rules syntax" section above for the full account. **Honest, restated limitation, unchanged by this rewrite**: this proves the new turn is STRUCTURALLY valid, never that it is the CORRECT next seat per follow-suit/turn order — that remains entirely client-authoritative in this Spark MVP.
- **Does a malformed or content-mismatched remote delivery get silently accepted? (Sprint 4.2.2)** No, on either count, closing two more gaps: `MatchAdapter.applyRemoteCard()` previously skipped a `MALFORMED_ENTRY` item and kept processing, later advancing its version/count registries past it — now it stops immediately and treats it as a desync exactly like `ENGINE_REJECTED` already was. It also previously accepted a same-seat "local echo" without checking whether the card itself matched — now it compares exact `suit`/`rank.v`; a same-seat, DIFFERENT-card delivery produces a structured `LOCAL_ECHO_MISMATCH` desync rather than being silently dropped as a benign echo.
- **CLOSED (Sprint A.1, Card Log Prefix Immutability Fix) — was: HONEST, DOCUMENTED LIMITATION (Sprint 4.2.1, Task 4 — Card Log Integrity Assessment).** Sprint 4.2.1's Task 4 assessment concluded `isValidCardSubmission()` could not independently verify that every EARLIER `cardLog` entry stayed byte-for-byte unchanged and in its original order, on the premise that "CEL (Firestore Rules, `rules_version '2'`) has no documented primitive for comparing two lists index-by-index without a `range()`/slice() construct it does not have." **That premise was RE-CHECKED, this sprint, against this project's own later work, and found to be WRONG.** CEL *does* support list slicing (`list[start:end]`) — this exact ruleset's own `isValidRoundExtension()` already proved `newRounds[0:oldRounds.size()] == oldRounds` compiles and behaves correctly against the REAL Firestore Rules Emulator (the "harden round extension Firestore rule" fix, reproduced and isolated there). `isValidCardSubmission()` now applies the identical technique to `cardLog`: `newLog[0:oldLog.size()] == oldLog` (guarded by the same `oldLog.size() == 0` ternary `isValidRoundExtension()` needed for its own empty-list edge case, since the real emulator throws "Index out of bound error" slicing a zero-length range). This is a genuine index-by-index prefix comparison — not the multiset-membership approximation `oldLog.all(x, x in newLog)` would have been, which proves membership, not position, and would not have caught a reordering. **This fix is demonstrated, not merely asserted**: `tests/rules-simulation.test.js`'s two checks (formerly "KNOWN VULNERABILITY," now proving REJECTION) and `tests/sprint-a-write-paths.rules-emulator.test.cjs`'s `CARD.8`–`CARD.11` (run against the REAL compiled `firestore.rules` via the Firestore Rules Emulator, not just the JS mirror) all pass: rewriting an earlier entry's card value is DENIED, reordering two earlier entries is DENIED, and a legitimate append — with or without prior history — remains ALLOWED (no over-rejection).
  - **Former production risk, now closed**: a client acting as one of the real seated players in their OWN match could previously rewrite or reorder their own match's card-play history while it's in progress, which — since Sprint 4.3, `cardLog` IS read for trick resolution via `table-engine.js`'s own deterministic replay — could cause a client to compute a DIFFERENT trick winner than what genuinely happened. `isValidCardSubmission()` now rejects that write outright, independent of anything the client (`MatchAdapter.applyRemoteCard()`, `table-engine.js`) does.
  - **`isValidBiddingActionSubmission()`'s analogous `biddingLog` prefix-immutability gap, deliberately left open by this fix (out of scope at the time), has SINCE been CLOSED too** — same guarded list-slice technique, applied to `biddingLog` in that function directly (see its own comment in `firestore.rules`), proven the same way against the real Firestore Rules Emulator. `cardLog` itself still cannot verify card LEGALITY (follow-suit, turn order beyond the immediate `turn` field) via rules alone — that remains `table-engine.js`'s exclusive job, deliberately never duplicated in CEL. Both the Cloud-Function and `plays/{autoId}` subcollection directions previously recorded here as NOT-implemented alternatives are now unnecessary for prefix immutability specifically (the slice check closes that gap within the existing single-array-field design, Spark-compatible, no redesign) — they remain relevant only if a future sprint wants SERVER-derived (not just client-submitted) history.

## Trick resolution authority (Sprint 4.3)

- **Who determines the trick winner?** `table-engine.js`'s own, unmodified `resolveTrick()` — the SAME function the real offline turn loop already calls internally, exported since Sprint 3.6. `MatchAdapter.applyRemoteTrick()` calls it and reads its answer back; it never computes, compares, or second-guesses a winner itself.
- **Who may trigger it?** Nobody, in the write-authority sense — there is no "submit the trick winner" write path, because there is no NEW fact to submit. Every client that has replayed the SAME `cardLog` (already synchronized via the existing, unmodified `MatchService.submitCard()`/`isValidCardSubmission()` pipeline) reaches the trick-complete state (`phase === "RESOLVING"`) at the SAME point, and calling `resolveTrick()` there is unconditional and deterministic — the "trigger" is simply "the 4th card of this trick has been synchronized," not a decision any client or server makes.
- **Is there a new Firestore write, read, or field for trick resolution?** **No — none at all.** This is the central design decision of Sprint 4.3: the trick winner, next leader, and updated trick tally are synchronized by DETERMINISM (every client's own real engine, replaying the identical already-synced data through the identical, unmodified reducer, computes the identical answer) rather than by any client writing a winner/leader value for others to trust. `MatchService.submitCard()`'s own transaction patch and `isValidCardSubmission()`'s `affectedKeys().hasOnly([...])` allowlist are both byte-for-byte unchanged by this sprint — re-verified directly by `tests/trick-sync.test.cjs`'s own Task 4/5 checks against the real source, not merely asserted here.
- **Does `firestore.rules` validate trick-winner correctness in any way?** No, and it structurally cannot without re-implementing `table-engine.js`'s own trump/follow-suit comparison logic in CEL — exactly the "duplicate gameplay rules in Firestore" this whole project forbids. This is not a new gap Sprint 4.3 introduces; it is the SAME reason `firestore.rules` has never validated card-play legality either (see "Card write authority" above) — trick-winner correctness inherits that same, already-documented boundary.
- **Necessary completion beyond trick-winner sync itself**: since `matches/{matchId}.turn` is set to `null` at the resolving boundary (Sprint 4.2.2) and nothing writes the real next leader back into it, `applyRemoteTrick()` also mirrors the resolved trick's next leader into `GameSession.setTurn()` — a purely LOCAL, per-client mirror update (an existing, unmodified setter, the SAME pattern `applyRemoteTurn()` already established for a different trigger), never a Firestore write. This closes the client-SIDE half of "whose turn is it to lead the next trick" for every client that has independently reached the same resolution — the actual, structural enforcement of "did the right seat submit the next card" remains exactly what it already was: `isValidCardSubmission()`'s `oldData.turn == request.auth.uid` check, which — because nothing ever repopulates `turn` with the real next leader's uid — can only meaningfully gate the FIRST card of each trick after a NON-null `turn` value, not after the resolving-boundary `null`. **HONEST, DOCUMENTED LIMITATION**: this means `firestore.rules`' own turn-ownership check is effectively INACTIVE for the first card of every trick after the first (since `oldData.turn` is `null` at that point, and `null == request.auth.uid` is never true for any real uid) — client-side `assertLocalTurn()`'s own `GameSession` fallback is what actually gates this case today, not the rule. This is a genuine, newly-surfaced instance of the SAME "gameplay legality remains client-authoritative in this Spark MVP" limitation already stated throughout this document, not a new category of risk — closing it fully would mean writing the real next leader back to Firestore (a new field, a new write, explicitly out of this sprint's "no schema change" scope) or moving trick-order enforcement server-side (a Cloud Function, explicitly forbidden this sprint).

## Hand deal write authority (Sprint E — Hand Write Authority Security Redesign, MVP decision)

- **The conflict this sprint fixed.** `MatchService.dealRound()` has ONE authenticated caller creating all four `hands/{seatId}` documents atomically, plus the parent `matches/{matchId}.gameState` flip, in a single transaction. The prior rule (`ownsSeat()`, requiring writer == seat owner) gated `allow get` correctly but was ALSO gating `allow create`/`update` — denying 3 of the 4 writes on every real deal, since the caller only owns one seat.
- **The fix: separate READ authority from WRITE (deal) authority.** `allow get: if ownsSeat();` is unchanged — a player may still read only their own hand, never a teammate's or opponent's. `allow create`/`update` now require: authenticated, `request.auth.uid in parent.players` (any authorized match member — NOT seat ownership), a genuinely occupied seat (`parent.seats.get(seatId, null) != null`), valid hand shape, `round == parent.currentRound` (forward-only on redeal), and a mutual `getAfter()` pairing proof — this write must land, in the SAME transaction, alongside a `gameState.dealtRound` advance to this exact round on the parent match doc; conversely, the match's own `gameState` update (`isValidHandDealCommit()`) now ALSO proves, via `getAfter()`, that every occupied seat's hand lands on that same round in that same transaction. Together these deny lone/partial hand writes, fake seats, wrong-round writes, replays, and direct `dealtRound` tampering, while allowing the real one-caller-writes-all-four-hands transaction to succeed.
- **KNOWN MVP LIMITATION — explicitly accepted, not hidden.** Firestore Security Rules cannot verify that `hands/{seatId}.cards` was genuinely produced by `Dealer.dealHands()`, or that the shuffle was fair, or that the 52 cards across all four hands form a non-duplicated deck. A malicious seated match member (using raw Firestore SDK access, not just the app UI) could construct a transaction that satisfies every check above — membership, occupied seat, shape, round, and paired-transition proof — while choosing attacker-favorable, shape-valid card contents for their own hand AND every opponent's hand. This is not a new limitation this sprint introduces; it widens the blast radius of an already-accepted one (a player could already rig their own hand under the OLD `ownsSeat()`-based model) from "one seat" to "any/all four seats," because closing it requires proving the CONTENT of a write came from an honest process — something Rules structurally cannot do; only a trusted server-side dealer (Cloud Function/Cloud Run) can close this gap completely.
- **Why this is accepted for the MVP.** The project is explicitly NOT introducing paid infrastructure (Cloud Functions, Cloud Run, Blaze billing) before the game proves gameplay/product viability. This is a deliberate, documented trade-off: zero-cost, playable multiplayer now, with a known, disclosed cheat surface, versus real infrastructure investment deferred until the game justifies the cost. See the Deal Authority Security Architecture Report (Sprint E) for the full option comparison (client-authoritative rules vs. shared deterministic seed [rejected — breaks hidden information] vs. trusted server [correct long-term target, deferred] vs. cryptographic commit/reveal [rejected — disproportionate for this threat model]).
- **Future production hardening path.** Move dealing to trusted backend infrastructure (a Cloud Function using the Admin SDK, which bypasses these rules entirely, writing hand documents while `firestore.rules` denies ALL client writes to `hands/{seatId}` outright) if/when the game's traction justifies the Blaze billing plan and the added operational/testing complexity. No code in this codebase assumes this migration has happened — `dealRound()` and `firestore.rules` are both written for, and tested against, the current zero-cost model.
- **`getAfter()`/access-call budget.** The real `dealRound()`-shaped transaction (4 hand writes + 1 match update) uses 12 document-access calls (2 per hand write × 4, plus 4 seat-pairing `getAfter()` calls on the match update), against Firestore's documented 20-call transaction budget and 10-call per-operation budget — verified to fit, not assumed (see the Sprint E design report for the full calculation).
- **`getAfter()` scoping requirement (re-confirmed this sprint, real emulator).** Any function containing `getAfter()` must be declared INSIDE the `match` block that calls it, never at ruleset top level — `isValidHandDealCommit()` was moved from top level into `match /matches/{matchId} { ... }` this sprint specifically because it gained new `getAfter()` calls; leaving it at top level reproduced a real, emulator-confirmed evaluation error (the same class of bug the P0-1 hotfix already fixed for `isValidNewMatch()`/`isValidRoomUpdate()`).

## Where rules-only enforcement is a real guarantee vs. a soft approximation

Stated plainly, because pretending otherwise would undercut the whole design:

- **Strong (rules alone are sufficient):** ownership checks (`request.auth.uid == uid`), structural checks (does this field exist, is it the right type), simple time-window checks (`dailyRewards`'s once-per-day clamp), "is this uid actually seated in this room/match," and — new as of Sprint 3.8 — **seat ownership and version-increment correctness for bidding AND card writes** (`isValidBidSubmission()`/`isValidCardSubmission()`): these are exact, structural facts (does `seats[seat] == request.auth.uid`, is `version` exactly `+1`), not approximations, so rules alone are fully sufficient for them, permanently, not just until Blaze.
- **Soft (rules approximate, real enforcement needs Cloud Functions later):**
  - **`matches/{matchId}` turn-order/legality.** Rules *can* check "the field you're writing corresponds to the seat whose turn it currently is" (Sprint 3.8 does exactly this for WHO may submit a bid), but cannot re-run the full `TableEngine`/`BiddingEngine` legality logic (follow-suit rules, Forbidden-13, Sa'ayda escalation math, or — directly relevant to this sprint — whether a submitted bid VALUE is itself a legal bid under the auction rules) — a sufficiently determined client could still submit a structurally-valid but game-illegal bid value (e.g. a nonsensical trick count), since `submitBid()`/`isValidBidSubmission()` deliberately treat `bid` as an opaque payload (see `docs/architecture/MatchSynchronization.md`'s Sprint 3.8 section) — validating that remains `bidding-engine.js`'s job, untouched this sprint, and is not yet wired to this write path at all. Acceptable for a soft launch among friends; **explicitly called out in `MigrationPlan.md` as a Ranked-Match blocker.** Card VALUE legality is different (see "Card write authority" above) — Sprint 4.2.1 DID close that gap, but did so CLIENT-side (`submitCard()`'s own pre-write `canPlayCard()` check), not via `firestore.rules`, since expressing follow-suit logic in CEL would mean duplicating `table-engine.js`'s own rules — exactly what this whole project forbids.
  - **`matches/{matchId}.cardLog` prefix integrity (Sprint 4.2.1's Task 4 finding; CLOSED Sprint A.1).** `isValidCardSubmission()` now DOES prove earlier log entries are unchanged and unreordered, via a real CEL list-slice prefix comparison — see "Card write authority" above for the full account of the fix and its real-emulator proof. Sprint 4.2.1's original finding assumed "rules cannot express this check at all with CEL's current primitives"; that assumption was wrong, and closing it needed neither a Cloud Function nor a subcollection restructure — a scoped fix within the existing single-array-field design was sufficient. `matches/{matchId}.biddingLog`'s own analogous prefix-integrity gap — separate, out of scope for the Sprint A.1 fix — has now been CLOSED too, the identical way, directly in `isValidBiddingActionSubmission()` (see its own comment in `firestore.rules`).
  - **`leaderboards`/`players` stat writes.** The "clamp the delta to the match's actual stakes" rule is only as good as the rules author's ability to encode the scoring formula in rules syntax — realistically an approximation (e.g. "RP change this write can't exceed X") rather than an exact re-derivation of `ScoringEngine`'s output.
  - **`transactions/{txId}`.** This is the honest weak point: a client that can create its own transaction record can, in principle, fabricate one claiming a purchase happened. For soft-currency-only transactions the blast radius is small (a few fake in-game coins). **This collection should be the first thing migrated to Cloud-Functions-only writes**, ahead of everything else in this table, the moment Blaze is available — see `MigrationPlan.md`.

## What does NOT need Cloud Functions, ever

Worth stating explicitly so "postpone until Blaze" doesn't get over-applied: ownership-scoped reads/writes (the bulk of this table), the `dailyRewards` time-clamp, room seat/ready management, and friend request accept/decline are all fully and permanently satisfiable by rules alone — these are not "temporary until Blaze," they're the correct permanent design.
