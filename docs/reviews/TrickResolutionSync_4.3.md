# Implementation Report — Sprint 4.3: Trick Resolution Synchronization

**A STRICT implementation sprint** — online trick-winner synchronization ONLY. Not scoring, not next round, not match end, not a redesign, not a refactor. `table-engine.js` remains the single, unmodified authority for trick winner, follow suit, trump, played cards, trick completion, and next leader.

## 1. Task 1 — Architecture Verification (performed FIRST, before any code)

**Question:** does `table-engine.js` already expose enough to determine trick completion, trick winner, and next leader, WITHOUT adding gameplay logic?

**Finding: YES.**
- **Trick completion**: `TableEngine.getState().phase === "RESOLVING"` — the EXISTING signal `emit()` itself already sets the instant the 4th card of a trick lands (unmodified `emit()` body, Sprint 3.6/4.2.1).
- **Trick winner / next leader**: `TableEngine.resolveTrick()` — exported since Sprint 3.6, the EXACT SAME function the real offline turn loop already calls internally (`advance()` → `sweepThenResolve()` → `resolveTrick()`). It computes the winner via its own internal `trickWinner()`, records it into `state.lastTrick.winnerId`, increments `state.tricksWon`, and advances `state.leaderId`/`state.turn`/`state.trickNo`/`state.phase` — all existing, unmodified behavior. `TableEngine.getState()` (also exported since Sprint 3.6) exposes every one of those fields afterward.

**No engine change was needed. No Architecture Blocker applies.** Re-verified directly (not just asserted) by `tests/match-adapter.test.cjs`'s own Task 1 check and `tests/trick-sync.test.cjs`'s own Task 1 check, both reading `table-engine.js`'s real source to confirm its export object is byte-for-byte unchanged by this sprint.

## 2. Task 2 — `MatchAdapter.applyRemoteTrick(matchId, matchDoc)`

Resolves AT MOST ONE completed trick per call. "Remote trick state" means exactly what this project has always meant by that phrase for card sync: the REAL `TableEngine` state, reached ONLY by replaying Firestore's own `cardLog` through the unmodified engine (via the EXISTING `applyRemoteCard()`, called separately — never duplicated). This function's ONLY direct engine call is `TableEngine.resolveTrick()`; the returned `winnerId` is read back from `TableEngine.getState().lastTrick.winnerId` AFTERWARD — never computed, compared, or second-guessed by this function.

Guarded by:
- `engineState.phase !== "RESOLVING"` → ordinary no-op (`NOT_RESOLVING`) — ALSO the correct outcome when an upstream `applyRemoteCard()` desync (`MALFORMED_ENTRY`/`LOCAL_ECHO_MISMATCH`/`ENGINE_REJECTED`) is exactly why the trick never completed; this function never re-derives or masks that detection.
- `lastResolvedTrickNoByMatch[matchId] === trickNo` → `ALREADY_RESOLVED`, an idempotent no-op.

**Deliberately does NOT gate on `matchDoc.cardPhase`** (unlike a version-number gate, which every OTHER `applyRemote*()` function uses): `cardPhase` reflects the phase immediately after the LATEST card only, not a reliable cross-check for a HISTORICAL trick being caught up on during a multi-trick catch-up pass (see Task 3). Documented as a deliberate design choice, not an oversight.

**Necessary completion, found during end-to-end testing**: `matches/{matchId}.turn` is set to `null` at the resolving boundary (Sprint 4.2.2) and nothing writes the real next leader back into it — there is no Firestore field for that (see Task 4/5's conclusion below). Without ALSO mirroring the resolved trick's next leader into `GameSession`'s own turn field, `assertLocalTurn()`'s EXISTING fallback (Sprint 4.1, unmodified) would keep reporting a stale seat, blocking every subsequent trick's first submission — turning "synchronize the winner" into a dead end after trick 1. `applyRemoteTrick()` therefore also calls `GameSession.setTurn()` — an EXISTING, unmodified public setter already established as safe to call from this file (Sprint 3.9, Sprint 4.1) — with the engine's own post-resolution `state.turn`, and ONLY when `phase === "PLAY"` (a genuine next trick exists to lead). This is the EXACT SAME "mirror the engine's decision into GameSession, never compute one independently" pattern `applyRemoteTurn()` already established, triggered by trick resolution instead of a Firestore turn-field change.

## 3. Task 3 — `MatchAdapter.startTrickSync(matchId)`

Reuses `MatchService.subscribeToMatch()` verbatim — confirmed by reading that function's own doc comment: a second/third/fourth call for the SAME matchId registers an additional local callback against the ONE already-active ref-counted entry; it never creates a second Firestore listener. Same shape as `startBidSync()`/`startTurnSync()`/`startCardSync()`.

**One documented, honest architectural necessity** beyond a single `applyRemoteX()` call per delivery: `cardLog` is append-only and never cleared across trick boundaries (Sprint 4.2's own documented design), so ONE delivery (a late subscriber, or a reconnect that missed several deliveries) can legitimately carry MORE than one already-completed-but-unresolved trick. `table-engine.js`'s own `emit()` correctly refuses a new card while `phase === "RESOLVING"` (existing, unmodified behavior), so catching up on N backlogged tricks requires N alternating "replay what's now unblocked, then resolve it" steps. `startTrickSync()`'s subscription callback is the ONE place this loop lives — it alternates the EXISTING, unmodified `applyRemoteCard()` (safe to call again — fully idempotent) and the new `applyRemoteTrick()`, capped at 13 iterations (the maximum possible tricks in one round), stopping the instant a pass resolves nothing further. This is orchestration, not a new algorithm — no gameplay rule is duplicated by looping calls to two functions that already, independently, refuse to do anything incorrect on a redundant or premature call.

## 4. Task 4 — MatchService: NOT MODIFIED

**Justification**: the trick winner, next leader, and updated `tricksWon` are ALL deterministically re-derivable, by EVERY client, from data ALREADY being synchronized (the existing `cardLog` + the existing, immutable `trump`/seat rules `table-engine.js` already enforces identically everywhere). There is no new FACT that needs a new Firestore write, because every client's own real engine, replaying the SAME already-synced cards through the SAME unmodified reducer, computes the IDENTICAL answer. This is "synchronization by determinism," not "synchronization by a broadcast write." No new field, no new write path — `MatchService` needed no change, and none was made. `MatchService.submitCard()` is byte-for-byte unchanged (re-verified directly by `tests/trick-sync.test.cjs`'s own Task 4 check against the real file's own transaction-patch source).

1. **Did you duplicate ANY gameplay rule?** NO. `applyRemoteTrick()`'s only engine call is `TableEngine.resolveTrick()`; the winner is read back from the engine's own output, never computed, compared, or re-derived independently anywhere in `match-adapter.js`. 2. **Did you modify table-engine.js?** NO. Byte-for-byte unchanged — re-verified directly by both test files reading the real file's own source and confirming its export object is untouched.
3. **Did you calculate a trick winner outside TableEngine?** NO. See #1.
4. **Did you introduce another Firestore listener?** NO. `startTrickSync()` calls the SAME, existing `MatchService.subscribeToMatch()` — confirmed by that function's own ref-counting doc comment and by this sprint's own end-to-end test (`ONSNAPSHOT_CALLS[key] === 1` even after a second, late subscription).
5. **Did you change Firestore schema?** NO. No new field was added anywhere. `buildInitialMatchDoc()`/`submitCard()`'s transaction patch/`isValidCardSubmission()`'s allowlist are all byte-for-byte unchanged — re-verified directly by `tests/trick-sync.test.cjs`'s own Task 4/5 checks against the real source.
6. **Did you touch forbidden files?** NO. Only `design-ui/match-adapter.js`, `tests/*`, and `docs/*` were modified. `table-engine.js`, `bidding-engine.js`, `scoring-engine.js`, `dealer.js`, `deck.js`, `cards.js`, `session.js` (GameSession/GameState), and every `MatchService.subscribeToMatch()`/`submitBid()`/`submitCard()` FUNCTION BODY are byte-for-byte unchanged — confirmed by the forbidden-scope sweep below (this Report's own diff-stat check against the full forbidden list).
7. **Did you fake any test?** NO. Every check is labeled MOCKED (real code, hand-written fake Firestore/fake engines where documented) or, for the pre-existing rules-simulation suite (untouched this sprint), SIMULATED. No test claims Firebase Emulator or real Firestore validation anywhere in this sprint's additions.
8. **Did any architecture decision deviate from this brief? If yes, document it clearly.** **YES, one, found only while writing the end-to-end tests, documented here and in `match-adapter.js`'s own comment:** `applyRemoteTrick()` also calls the EXISTING `GameSession.setTurn()` setter after a successful resolution (only when a genuine next trick exists to lead). This was NOT anticipated in the original Task 2 wording, which only asked for winner/next-leader detection. It became NECESSARY once end-to-end testing showed that without it, `assertLocalTurn()`'s pre-existing fallback (Sprint 4.1, unmodified) would keep reporting a stale turn-holder after every trick resolution, blocking all further play — turning "synchronize the winner" into a dead end. The fix reuses an EXISTING, unmodified `GameSession` setter this file already calls elsewhere for the identical purpose (mirroring an engine decision into `GameSession`, never computing one independently) — it does not touch `MatchService`, `table-engine.js`, or Firestore, and does not introduce any new rule. No other deviation occurred: no gameplay rule was duplicated, no forbidden file was touched, no new Firestore write path was created, and no test was faked.

   **A second, related fact surfaced by the SAME investigation, not a deviation but an honest limitation worth stating plainly**: because nothing writes the real next leader's uid back into `matches/{matchId}.turn` in Firestore (only the local `GameSession` mirror is updated, per the fix above), `firestore.rules`' own `isValidCardSubmission()` turn-ownership check (`oldData.turn == request.auth.uid`) is effectively INACTIVE for the first card of every trick after the first — `oldData.turn` is `null` at that point (set by `submitCard()` at the resolving boundary, Sprint 4.2.2), and `null == request.auth.uid` is never true for any real uid. The CLIENT-side `assertLocalTurn()`/`GameSession` fallback is what actually gates this case today, not the rule. This is a genuine, newly-surfaced instance of the SAME "gameplay legality remains client-authoritative in this Spark MVP" limitation already stated throughout this project's docs, not a new category of risk — see `docs/architecture/SecurityArchitecture.md`'s new "Trick resolution authority" section for the full account. Closing it fully would mean writing the real next leader back to Firestore (a new field, a new write — explicitly out of this sprint's "no schema change" scope) or moving trick-order enforcement server-side (a Cloud Function — explicitly forbidden this sprint).

## 10. Conclusion

One necessary, honestly-documented completion (mirroring the resolved trick's next leader into `GameSession`) was added beyond the brief's original wording, closing the gap that would otherwise have made trick resolution a dead end after the first trick. Stopping here per the brief's stop condition — no Score Synchronization, Match End, Next Round, Voice Chat, Replay, AI, Matchmaking, or Cloud Functions were started. Waiting for review.
